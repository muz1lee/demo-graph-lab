# 研究方案

## 研究问题

一段机器人示范最有价值的内容，不是每一帧的轨迹，而是：

- 任务要分成哪些阶段；
- 每个阶段必须保持或达到什么关系；
- 哪些数值必须在新场景里重新感知；
- 当前阶段的选择会不会让后续阶段无解。

本项目研究如何把这些信息编译成一条可执行、可检查的约束链。目标不是复刻示范轨迹，而是在新场景中保留示范所表达的任务结构。

## 核心假设

长程操作中，很多失败并不是控制器没有到位，而是更早的选择破坏了后续可行性。例如：抓试管的位置本身可抓，却让插入时夹爪撞到试管架。

我们的假设是：

> 如果候选选择同时考虑当前约束和后续约束，长程任务会比只看当前阶段的贪心选择更稳定，而且失败更容易归因。

约束链在系统里承担三项职责：

1. 约束候选选择；
2. 定义每个阶段的独立验收条件；
3. 把失败定位到具体阶段和具体约束。

## 方法流程

```text
示范视频
  → 阶段、对象和关键帧
  → constraints + acceptance + typed holes
  → 只调用高层 Runtime API 的 policy
  → 运行时感知并生成候选
  → 候选过滤、排序和下游检查
  → 执行动作
  → 独立 gate 验收
  → 失败归因或有界恢复
```

当前仓库已经实现示范解析、约束图、policy 编译、顺序执行和 Oracle 联调。真实候选源、非特权感知、下游可行性检查和自适应恢复仍未实现。

## 约束图

每个阶段只保留四类信息：

- `stage_objects`：当前操作对象和目标对象；
- `constraints`：动作过程中应满足的关系；
- `acceptance`：阶段结束时独立检查的关系；
- `holes`：新场景中必须重新求解的数值，如抓取位姿、轴、目标点和停止条件。

示范只提供符号关系和离散偏好。世界坐标、角度、距离和接触阈值不能由 VLM 猜测，必须由运行时观测或规划器得到。

## 候选选择

候选选择分三步，各自回答不同问题：

1. **硬过滤**：这个候选是否可达、无碰撞、满足夹爪宽度等基本物理条件？不满足就删除。
2. **示范排序**：在剩余候选中，哪个更符合示范给出的抓取区域、接近方向和对象关系？这里只改顺序，不删除候选。
3. **下游检查**：这个候选是否至少保留一个可行的后续选择？

最后一步可以写成一个简单递归：当前候选可行，当且仅当它满足本阶段约束，并且存在一个与它兼容的下一阶段候选；末阶段只检查自身约束。

这种“先看后续是否还走得通”的思路在规划领域并不新。本项目的研究点，是把它落实到单段示范产生的定性约束链上，并用真实候选和阶段级实验检验它是否有用。

不采用复制仿真状态后再向前试跑的方案。它计算重，也会让仿真内部信息进入方法路径。下游检查只使用主方法允许获得的几何与规划结果。

## VLM 的职责

VLM 可以参与四个位置，但权限不同：

- 从示范中提取阶段、对象和约束；
- 根据约束图合成只调用高层 API 的 policy；
- 在运行时对少量离散候选排序，并引用支持选择的约束；
- 根据真实执行后的残差提出有界、离散的修正建议。

VLM 不得：

- 直接输出世界坐标、关节角、速度或力控制量；
- 调用底层 pipeline 或机器人控制接口；
- 读取 simulator 精确状态；
- 决定某个阶段是否通过。

运行时 VLM 的候选排序、修正和视觉证据接口目前只是设计，尚未实现。完整接口边界见 `API.md`。

当前 policy 步骤仍是 synthesis，而非纯机械编译：graph 没有完整声明 primitive sequence 和参数 wiring，backend 会补出这部分高层 workflow。该 policy 在执行前通过静态检查和 fake dry-run，并在同一组选择实验中固定复用；backend 不在 episode 中重新规划。若后续发现这一步随机性过大，再把 action wiring 纳入 graph 并改用确定性模板，不把代码生成本身扩成研究主张。

## 后续学习方向（当前不实施）

显式的下游可行性检查以后可以作为 teacher 和 verifier，为每个候选产生结构化标签：当前不可行、当前可行但后续无解、至少保留一条后续路径，或无法判断。真实或仿真的 forward rollout 再提供动作后的观测、gate 结果和最终任务回报。两类数据不能混为一谈：未执行候选只有 planner label，只有实际执行的候选才有真实 transition。

未来的学习问题限定在高层候选选择：

- 状态是非特权观测、当前与剩余约束、阶段历史和当前候选集；
- 动作是一个 stage-level candidate ID，以及 `reobserve / abstain / abort`；
- SFT 学习候选排序或兼容性预测；
- RL 学习几何检查未覆盖的真实成功概率，如滑脱、感知误差和控制不确定性；
- 碰撞、可达、力限制、opaque handle 和独立 gate 继续留在可信代码中。

这个方向不进入当前 TODO 或 milestone。只有非特权完整 episode、真实候选日志和显式下游检查都稳定后，才评估是否开始 SFT 或 RL。当前只要求日志保留完整候选、过滤与兼容结果、最终选择和 gate 结果，避免未来缺少训练所需的反事实数据。

## 可证伪实验

### 约束图是否有用

固定模型、感知、候选和执行预算，对比：

- 无示范的通用 agent；
- 文本步骤计划；
- 当前阶段约束图；
- 带下游检查的约束链。

如果约束链没有提升成功率，也没有改善第一失败点的定位，主张不成立。

### 示范排序是否真的改变选择

固定同一候选集，只改变示范中的 `region_grasp` 或 `approach_direction`，检查 top-1 是否按预期改变，并记录真实执行结果。

如果排序很少改变 top-1，或者改变后没有收益，就不把它作为主要贡献。

### 下游检查是否优于贪心

构造局部最优但后续必死的候选对，再在真实任务中寻找同类耦合。比较只看当前阶段与向后检查若干阶段的结果。

如果兼容性判断成本接近直接执行，或误判太多，就退回“硬过滤 + 示范排序”，不继续扩大方法主张。

### Gate 是否改善归因

每次失败必须能记录：阶段、约束、观测证据和执行层错误。若 gate 只能给出模糊的任务失败，而不能稳定区分感知、选择、规划和执行问题，则需要先修验证系统，不能继续堆恢复模块。

## 不做什么

- 不做端到端 VLA 训练；
- 不把 demo-to-code 本身当作新颖性；
- 不复制仿真状态后向前试跑；
- 不在当前项目中积累技能库或自动发现新 API；
- 不在完整非特权 episode 打通前扩展到大规模 benchmark 或理论结论。
